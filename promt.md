# 2. Назначение системы

Ollama Monitor — локальное веб-приложение для наблюдения за работой Ollama.

Основная задача — предоставлять максимально подробную информацию о работе моделей искусственного интеллекта.

Система должна отвечать на следующие вопросы:

- Какие модели установлены?
- Какие модели сейчас загружены?
- Какая модель обрабатывает запрос?
- Кто отправил запрос?
- С какого IP-адреса поступил запрос?
- Когда поступил запрос?
- Сколько времени выполнялся запрос?
- Сколько входных токенов обработано?
- Сколько выходных токенов сгенерировано?
- Какова скорость обработки входного контекста?
- Какова скорость генерации ответа?
- Сколько времени заняла загрузка модели?
- Сколько времени прошло до первого токена?
- Какие запросы выполняются прямо сейчас?
- Какие запросы завершились с ошибкой?
- Как изменяется скорость модели со временем?
- Как загружены видеокарты?
- Сколько видеопамяти занято?
- Используется ли несколько GPU?
- Какова средняя производительность каждой модели?
- Какие приложения чаще всего используют Ollama?
- Как изменяется производительность при увеличении контекста?
- Какова производительность разных моделей на одинаковом оборудовании?

Система должна быть полезна для сравнения моделей и оценки их пригодности для автономных программирующих агентов.

# 4. Архитектура

Система должна поддерживать два режима работы.

## Режим 1. Passive Monitoring

Пассивный мониторинг существующего сервера Ollama.

Приложение подключается к Ollama и получает доступную информацию без изменения существующих клиентов.

Источники данных:

- Ollama REST API.
- Ollama server.log.
- NVIDIA Management Library.
- nvidia-smi.
- psutil.

В этом режиме необходимо отображать:

- Доступность Ollama.
- Установленные модели.
- Загруженные модели.
- Использование GPU.
- Использование видеопамяти.
- Состояние сервера.
- Системные показатели.
- HTTP-запросы, обнаруженные в server.log.
- IP-адреса клиентов, если они присутствуют в логах.
- Продолжительность запросов, если она присутствует в логах.
- Ошибки сервера.

Важно:

Пассивный режим не позволяет гарантированно получить точное количество токенов, название модели или скорость генерации для каждого исторического запроса.

Не пытаться выдумывать недоступные показатели.

Необходимо явно показывать источник и степень достоверности данных.

## Режим 2. Proxy Monitoring

Основной режим полноценного мониторинга.

Все приложения подключаются к Ollama через Ollama Monitor.

Схема:

```text
                ПРИЛОЖЕНИЯ
                     |
        +------------+------------+
        |            |            |
     OpenCode      VS Code      Python API
        |            |            |
        +------------+------------+
                     |
                     v
           OLLAMA MONITOR
              PORT 8881
                     |
        +------------+------------+
        |                         |
    Web Interface             API Proxy
        |                         |
        |                         v
        |                  Ollama :11434
        |                         |
        |                         v
        |                    GPU / CPU
        |
        +---- SQLite
        |
        +---- GPU Monitor
        |
        +---- Statistics
```

Приложение должно корректно проксировать запросы к Ollama и собирать статистику.

Главное требование:

**Монитор не должен заметно замедлять генерацию модели.**

# 5. Прокси-сервер Ollama API

## 5.1. Поддерживаемые маршруты

Необходимо поддержать все стандартные маршруты Ollama API посредством прозрачного проксирования.

В частности:

- POST /api/generate
- POST /api/chat
- POST /api/embed
- POST /api/embeddings
- GET /api/tags
- GET /api/ps
- POST /api/show
- POST /api/pull
- POST /api/push
- POST /api/create
- DELETE /api/delete
- POST /api/copy
- GET /api/version

Также необходимо поддержать OpenAI-совместимые маршруты Ollama:

- POST /v1/chat/completions
- POST /v1/completions
- POST /v1/embeddings
- GET /v1/models

Архитектура должна позволять проксировать и новые маршруты Ollama без изменения исходного кода для каждого маршрута.

Нельзя ограничиваться только перечисленными API.

## 5.2. Прозрачность проксирования

Прокси должен максимально точно сохранять:

- HTTP-метод.
- Путь.
- Query parameters.
- Тело запроса.
- Content-Type.
- Поддерживаемые заголовки.
- HTTP-статус.
- Формат ответа.
- Потоковую передачу данных.
- Сообщения об ошибках.

Необходимо корректно обрабатывать:

- JSON.
- NDJSON.
- Server-Sent Events.
- Обычные HTTP-ответы.
- Большие тела запросов.
- Multipart-запросы.
- Потоковую загрузку и скачивание данных.
- Отключение клиента.
- Отмену запросов.
- Тайм-ауты.
- Одновременные запросы.

Не буферизовать весь потоковый ответ перед отправкой клиенту.

Не изменять содержимое ответов Ollama.

Не передавать upstream некорректные hop-by-hop HTTP-заголовки.

Не допускать рекурсивного проксирования запросов обратно на порт 8881.

## 5.3. Streaming

Особенно тщательно реализовать потоковые ответы.

Ollama использует потоковую передачу JSON-объектов для ряда API.

Пример:

```json
{"model":"example","response":"Hello","done":false}
{"model":"example","response":" world","done":false}
{"model":"example","done":true,"eval_count":100,"eval_duration":5000000000}
```

Прокси должен:

1. Получать данные от Ollama.
2. Немедленно передавать их клиенту.
3. Параллельно анализировать поток.
4. Извлекать статистику из завершающего объекта.
5. Сохранять результаты в SQLite.
6. Обновлять веб-интерфейс.

Парсер должен учитывать, что границы сетевых чанков не совпадают с границами JSON-объектов.

Необходимо поддержать корректную обработку NDJSON и SSE.

Для OpenAI-совместимого API статистика использования токенов может отсутствовать в потоке. При наличии поддерживаемого механизма получения usage использовать его, но не подменять отсутствие статистики вымышленными значениями.

# 6. Статистика запросов

Для каждого запроса создавать уникальный идентификатор UUID.

Сохранять следующие данные.

## 6.1. Основная информация

- ID запроса.
- Время поступления.
- Время завершения.
- IP клиента.
- Порт клиента, если доступен.
- HTTP-метод.
- API endpoint.
- Название модели.
- Тип операции.
- HTTP-статус.
- Статус выполнения.
- Размер запроса.
- Размер ответа.
- User-Agent.
- Идентификатор приложения, если передан клиентом.
- Режим мониторинга.
- Источник статистики.

Типы операций:

- chat
- generate
- embedding
- model_load
- model_pull
- model_create
- other

## 6.2. Временные показатели

Измерять:

- Полную продолжительность запроса.
- Время загрузки модели.
- Время обработки входного контекста.
- Время генерации ответа.
- Время до первого байта.
- Время до первого токена, если его можно достоверно определить.
- Время передачи ответа клиенту.

Использовать монотонные таймеры Python для измерения длительности.

Не путать время первого байта с временем первого токена.

Не путать время, измеренное прокси, с временем, возвращённым Ollama.

## 6.3. Статистика токенов

Для Ollama Native API извлекать:

```json
{
  "total_duration": 12500000000,
  "load_duration": 120000000,
  "prompt_eval_count": 2500,
  "prompt_eval_duration": 1100000000,
  "eval_count": 450,
  "eval_duration": 9800000000
}
```

Рассчитывать:

Скорость генерации:

`eval_count / (eval_duration / 1_000_000_000)`

Скорость обработки контекста:

`prompt_eval_count / (prompt_eval_duration / 1_000_000_000)`

Дополнительно рассчитывать:

- Среднюю скорость генерации модели.
- Минимальную скорость.
- Максимальную скорость.
- Медианную скорость.
- P95 продолжительности запросов.
- Общее количество обработанных токенов.
- Общее количество сгенерированных токенов.
- Среднюю длину входного контекста.
- Среднюю длину ответа.

Обязательно проверять деление на ноль.

Если статистика отсутствует, сохранять NULL.

Не заменять неизвестные значения нулями.

# 8. Мониторинг GPU

Реализовать отдельный компонент GPU Monitor.

Основной способ получения информации:

NVIDIA Management Library через Python.

Резервный способ:

`nvidia-smi`

Поддерживать несколько видеокарт.

Для каждой GPU отображать:

- Название.
- Индекс.
- UUID.
- Общий объём VRAM.
- Используемый объём VRAM.
- Свободный объём VRAM.
- Загрузку GPU.
- Загрузку контроллера памяти, если доступна.
- Температуру.
- Потребляемую мощность.
- Power Limit.
- Частоту GPU, если доступна.
- Частоту памяти, если доступна.

Информация должна обновляться автоматически.

Период обновления по умолчанию:

**1 секунда.**

Сделать период настраиваемым.

Если установлены две видеокарты, отображать каждую отдельно.

Пример:

```text
GPU 0 — Tesla V100 16 GB

VRAM: 12.4 / 16 GB
GPU Load: 95%
Temperature: 68°C
Power: 215 W


GPU 1 — RTX A4000 16 GB

VRAM: 8.2 / 16 GB
GPU Load: 72%
Temperature: 61°C
Power: 125 W
```

Значения условные.

Дополнительно отображать суммарный объём видеопамяти всех GPU.

При этом не считать суммарную VRAM единым непрерывным адресным пространством.

Если NVML не предоставляет какой-либо показатель, показывать «Н/Д».

Приложение должно продолжать работать при отсутствии NVIDIA GPU.

## 8.1. История GPU

Периоды:

- Последние 5 минут.

# 11. Активные запросы

Реализовать отслеживание запросов в реальном времени.

При поступлении запроса:

1. Создать запись.
2. Присвоить статус RUNNING.
3. Отобразить запрос на Dashboard.
4. Зафиксировать время начала.

Во время выполнения:

- Отображать прошедшее время.
- Показывать модель.
- Показывать клиента.
- Обновлять доступную информацию.

При завершении:

- Извлечь итоговую статистику.
- Присвоить статус COMPLETED.
- Сохранить запись.

При ошибке:

- Присвоить статус ERROR.
- Сохранить диагностическую информацию.

При отмене:

- Присвоить статус CANCELLED.

После аварийного завершения самого монитора незавершённые записи предыдущего запуска должны получать статус INTERRUPTED.

Важно:

Не выдавать скорость генерации в реальном времени за точную метрику Ollama, если она оценивается по сетевому потоку.

Допускается показывать приблизительную текущую скорость, но она должна иметь соответствующую маркировку.

# 15. Производительность

- Переиспользование HTTP-соединений.
- Отсутствие синхронных блокирующих операций в обработчиках.
- Неблокирующая запись статистики.
- Минимальная обработка каждого сетевого чанка.
- Отсутствие полного буферизования потоковых ответов.
- Ограничение памяти очередей.
- Корректная обработка backpressure.

Целевой ориентир:

Дополнительная задержка прокси должна быть минимальной.

Провести измерения прямого подключения к Ollama и подключения через монитор.

Не утверждать, что накладные расходы меньше определённого процента, пока это не подтверждено тестированием.

# 16. Безопасность

По умолчанию веб-сервер должен слушать:

`127.0.0.1:8881`

Разрешить настройку:

`0.0.0.0:8881`

для доступа из локальной сети.

При использовании `0.0.0.0` необходимо предусмотреть защиту интерфейса и API.

Реализовать настраиваемую авторизацию по токену либо другой подходящий механизм.

Не доверять произвольным X-Forwarded-For и аналогичным заголовкам без явно настроенного доверенного прокси.

Не сохранять по умолчанию:

- Полные тексты пользовательских запросов.
- Сгенерированный код.
- Пароли.
- API-ключи.
- Секретные заголовки.
- Персональные данные из тел запросов.

По умолчанию сохранять только метаданные и статистику.

Если впоследствии будет добавлено сохранение содержимого запросов, оно должно быть отключено по умолчанию и включаться явно.

Защитить приложение от:

- Некорректного JSON.
- Чрезмерно больших запросов.
- Неограниченного накопления логов.
- Неограниченного роста базы данных.
- Неконтролируемых фоновых задач.
- SSRF через произвольное изменение upstream URL.

Не выводить секретные значения в логах.
